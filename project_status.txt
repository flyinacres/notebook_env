PROJECT ENVIRONMENT-LOCK: ARCHITECTURE AND ROADMAP

CORE PHILOSOPHY:
A self-contained Python snapshot tool for Jupyter notebooks. Prevents dependency failures when distributing notebooks by embedding deterministic environment setup blocks into Cell 2 of .ipynb files.

KEY ARCHITECTURAL DECISIONS:

GENERATION STRATEGY (In-Environment Static AST):

Inspects the author's active working environment via importlib.metadata.

Uses static ast parsing to target only explicit top-level imports.

Strips hardware build tags (e.g., torch2.3.0+cu121 becomes torch2.3.0) so pip resolves local hardware binaries cleanly.

Embedded directly in Cell 2 of the notebook so it acts as a self-contained artifact.

BATCH PROCESSING STRATEGY:

Operates as a fast, static linter directly against the active environment across a directory of .ipynb files.

No headless nbconvert subprocess execution during generation. Pure AST parsing and metadata lookup only.

VALIDATION AND SMOKE-TESTING STRATEGY (Separate Harness):

A standalone test script used for CI/CD verification.

Creates a clean temporary .venv, runs pip install -r pinned_requirements.txt, and executes the notebook headlessly.

No complex auto-patching magic. If it fails, it reports a clear diagnostic (e.g., Missing scipy in Cell 4) so the author can manually tweak their lockfile.

TASK LIST AND IMPLEMENTATION ORDER:

Features & Enhancements NOT Yet Implemented (Missing/Optional Backlog)
If you plan to evolve notebook_env.py beyond v18, here are the primary gaps and potential future features based on our past discussions:

1. Automated Cell Injection (Writing directly into .ipynb files)
Current State: The script outputs the Step 1 Markdown and Step 2 Code blocks to stdout, requiring the author to copy and paste them into Cell 1 and Cell 2 manually.

Missing Feature: A programmatic --write or --inject CLI flag that parses the .ipynb JSON structure, prepends or overwrites the first two cells directly, and saves the file back to disk.

2. Conda / Non-Pip Environment Detection
Current State: The script relies entirely on sys.executable -m pip freeze and PyPI naming conventions.

Missing Feature: Handling packages installed exclusively via conda or non-standard system channels that do not register cleanly under pip list/pip freeze (e.g., system C++ libraries or CUDA toolkits installed outside pip).

3. Dynamic Package Name Aliasing Beyond IMPORT_TO_PYPI_MAP
Current State: Handled via a static dictionary (cv2 → opencv-python, sklearn → scikit-learn, PIL → Pillow, etc.).

Missing Feature: Dynamic metadata lookup (e.g., inspecting importlib.metadata or pkg_resources at runtime) to resolve obscure or newly installed third-party package import names that aren't hardcoded in IMPORT_TO_PYPI_MAP.

4. Automated Dry-Run / Verification Mode
Current State: The author runs notebook_env.py to obtain the blueprint, but testing whether pinned_requirements.txt installs cleanly requires running Cell 2 inside the notebook manually.

Missing Feature: A --test or --verify flag in notebook_env.py that spins up a temporary virtual environment (venv), attempts a trial pip install -r pinned_requirements.txt, and verifies that all top-level imports load successfully before generating the output text.

Worth separating what's actually lost from what's actually kept, since "misses so much" is true but not evenly true across the tool's outputs.

What tool 2 cannot do at all, since there's no live kernel: confirm installed versions, confirm GPU availability, catch dynamic imports. Those are real, permanent gaps, not implementation debt, they're the difference between static and live inspection.

What it can still do reliably, since AST extraction is solid regardless of execution: produce the list of top level imports and map them to likely pypi package names, same as tool 1's static half. On its own that's not very differentiated. Someone can eyeball a notebook's imports in a few seconds, and pipreqs already does roughly this for plain scripts.

Two things worth separating out, since they change the calculus:

First, if the notebook's own code contains explicit pinned installs (!pip install torch==2.3.1), that's real, verifiable evidence you can harvest with the same regex approach already built for index URLs. Author intent captured in the file itself is a different and stronger signal than "we guessed the version from nothing."

Second, and this is the one from your original project overview that hasn't been touched since the reframe: correlating a notebook's run date or kernel metadata against Kaggle's docker-python changelog to infer what the base image probably contained at that time. That's the one piece of value here that nothing else, not tool 1, not pipreqs, not collect_env, provides. It's an estimate, not a confirmed fact, but it's a genuinely useful estimate for exactly the failure mode your project overview names, silent breakage months later from base image drift.

So I'd reframe the question. Tool 2 isn't a weaker version of tool 1, it's a different kind of tool answering a different question: not "what did this notebook confirm it used" but "what does the evidence in this file suggest it probably needs." As long as it's presented that way, hedged, evidence graded (explicit pin found vs. inferred from changelog vs. bare import with no version signal at all), it's consistent with the honesty bar you've held throughout. Where it'd become not worthwhile is if it gets presented with false confidence, a plain unpinned import shouldn't come out looking as solid as an explicit pin found in the code.

Is the changelog correlation piece actually appealing to you still, or has your interest genuinely moved to tool 1 and this is more of a "should I officially retire it" conversation?

FINDINGS FROM A BROADER TEST
Confirmed issues found in real-world testing

Batch mode's strict=True metadata gate rejected any notebook lacking kernelspec/language_info entirely, not just genuinely non-Python ones. Fixed today, 97/97 tests still pass.
Platform-injected pseudo-modules reported as "uninstalled" when they're not installable at all: dbutils (Databricks), kaggle_secrets (Kaggle). Two independent real-world hits now, same underlying category. Unresolved.
Possible local, repo-relative imports (cookbook, runners, tools, utils in the Databricks corpus) misreported as missing third-party packages. Still unconfirmed, waiting on you checking those notebooks' actual code.
Two concrete IMPORT_TO_PYPI_MAP misses: dotenv (should resolve to python-dotenv) and mpl_toolkits (should resolve to matplotlib, it's a namespace subpackage not a standalone distribution). Unresolved.
GPU detection blind spot: inspect_gpu_environment only checks direct imports for {"torch","tensorflow","jax"}. GTXvsRTX notebooks use fastai wrapping torch as a transitive dependency, so zero hardware signal fired on notebooks whose entire point is GPU comparison. This is the most significant one given hardware detection is a headline feature.
torch showing "uninstalled" on foreign notebooks: not a bug, expected behavior for a static scan of someone else's notebook in your bare local venv. Worth remembering as a permanent caveat when reading these reports, not something to fix.
Cosmetic: SyntaxWarning: invalid escape sequence noise from ast.parse on notebooks with unescaped \d, \w, \l, \g, \S in non-raw strings. Doesn't affect correctness, just stderr noise.
New, just noticed while compiling this: generate_batch_analysis_report never calls harvest_cell_magics_and_commands or surfaces auxiliary/magic-installed packages. It only reports on direct AST imports via build_manifest_entries. So every batch report you've read so far is blind to anything installed only via %pip/!pip magic and not directly imported — --batch (analysis) and --output (per-notebook cells) use genuinely different, non-overlapping detection logic, and you haven't been seeing the magic-harvesting half of the tool at all in these runs.

1. BATCH & OUTPUT DISCREPANCY (CELL MAGICS)
• Cause: walk_and_scan_directory() omits harvest_cell_magics_and_commands().
• Fix: Run magic harvester in batch loop; attach harvested_pkgs & index_urls to NotebookScanResult; include in report analysis.

2. GPU DETECTION BLIND SPOT (TRANSITIVE WRAPPERS)
• Cause: inspect_gpu_environment() checks direct imports only (torch, tf, jax). misses wrappers like fastai, keras, flax.
• Fix: Define TRANSITIVE_FRAMEWORK_MAP = {"fastai": "torch", "keras": "tensorflow", "flax": "jax"}. Expand inspected set before running hardware probes.

3. PLATFORM PSEUDO-MODULES (dbutils, kaggle_secrets)
• Cause: Static AST flags platform-injected runtime objects as missing PyPI packages.
• Fix: Define PLATFORM_PSEUDO_MODULES set. Intercept matching imports and flag as runtime-provided in manifest comments.

4. REPO-RELATIVE / LOCAL IMPORTS
• Cause: Relative helper modules (cookbook, utils) misidentified as missing third-party dependencies.
• Fix: Probe notebook parent/repo dir for matching local .py files or package directories. Flag matches as local repo modules.

5. MAP MISSES (dotenv, mpl_toolkits)
• Cause: Missing import-to-distribution mappings.
• Fix: Add "dotenv": "python-dotenv" and "mpl_toolkits": "matplotlib" to IMPORT_TO_PYPI_MAP.

6. AST SYNTAXWARNING NOISE
• Cause: Python 3.12+ ast.parse emits SyntaxWarning on unescaped backslashes in non-raw strings.
• Fix: Wrap ast.parse in warnings.catch_warnings() filter inside extract_imports_from_sources().
